你是一名资深桌面应用和 Agent 工程师。请在 `F:\play_tool` 中实现一个完整的 Windows 桌面项目，让视觉大模型通过游戏窗口体验 GAL 和文字 RPG，并记录不同模型在剧情中的选择。

请先检查目录和项目约定，再分阶段实施。以下是完整需求和技术方案，不要只输出概念设计或界面原型。

**一、项目目标**

用户启动应用后，通过主窗口配置模型接口、选择游戏窗口、创建会话，然后启动 Agent。

Agent 通过截图读取剧情，通过模拟鼠标和键盘推进对话、选择选项。用户可以通过悬浮窗观察状态、暂停、接管和输入引导。

项目重点是观察模型如何理解剧情、人物关系和剧情分支。优先支持窗口化、以对话和选项为主、没有严格操作时限的游戏。

采用通用核心和可选游戏配置，不将程序绑定到某一款游戏。不同游戏的兼容性需要实际验证，不能宣称支持所有文字 RPG。

**二、确定的技术架构**

采用前后端分离的本地桌面架构：

- 前端：React + TypeScript。
- 桌面外壳：Electron。
- 后端：Python + FastAPI。
- 前后端通信：HTTP 控制接口和 WebSocket 状态事件。
- 数据持久化：SQLite，截图独立保存。
- 图像处理：OpenCV，按需要使用。
- 窗口捕获：Windows Graphics Capture。
- 输入执行：封装 Win32 鼠标和键盘接口。
- 模型调用：自定义 Provider 接口，底层可使用 LiteLLM。
- 数据结构校验：Pydantic。

Electron 负责主窗口、悬浮窗、后端生命周期及打包入口。后端负责捕获、模型请求、剧情记忆、动作执行和数据库。

本地后端只监听回环地址，使用每次启动生成的访问凭据。前端不能直接获得任意系统命令执行能力。

先验证捕获库能否准确绑定窗口句柄。不能仅凭窗口标题识别目标；如果封装无法满足要求，补充原生桥接，不自动退化为整个桌面截图。

**三、主窗口**

主窗口包含以下功能：

1. 会话侧边栏。
2. 模型连接配置。
3. 选择游戏窗口按钮。
4. 当前游戏窗口预览。
5. 开始、继续和暂停按钮。
6. 当前运行状态。
7. 剧情观察、选择和操作记录。
8. 引导输入框。
9. 模型请求错误及恢复提示。

模型配置包含：

- 配置名称。
- API URL。
- API Key。
- 模型名称。
- 接口类型。
- 测试连接按钮。

允许保存多份模型配置。模型名称支持手动填写，接口不提供模型列表时仍然可用。

连接测试分别验证接口可访问和图片输入可用，显示明确结果。区分认证失败、地址错误、模型不支持图片、超时、限流和输出格式错误。

API Key 使用系统凭据存储。数据库只保存密钥引用，日志、导出文件和版本库不包含密钥。凭据存储失败时明确报告，不静默改为明文保存。

界面以普通用户能够理解的语言展示状态，避免暴露无助于操作的内部实现细节。

**四、会话管理**

会话管理类似常见聊天应用，但创建流程保持简单。

创建会话时：

- 只要求用户填写会话名称。
- 名称不能为空。
- 允许不同会话使用相同名称。
- 不要求填写游戏名称、存档信息或模型配置。
- 模型配置和游戏窗口在主界面选择。

支持：

- 新建会话。
- 打开已有会话。
- 修改会话名称。
- 删除会话。

每个会话使用独立 ID，名称修改不影响历史数据。

新建会话必须拥有空白的聊天记录、剧情记忆和引导记录。不同会话不能共享人物关系、摘要、历史选择或检索结果。

模型连接配置可以复用，但会话中的运行配置需要记录，方便解释实验结果。更换模型后记录新的运行段及配置，不覆盖此前模型的信息。

删除正在运行的会话前，先停止该会话并使所有待处理动作和模型响应失效。删除其记录、记忆、检查点及所属截图，不操作游戏本身的存档。

后台延迟返回的响应不能重新创建已删除会话，也不能写入其他会话。

第一版允许保留多个会话，同时只运行一个 Agent。切换运行会话时先暂停当前会话，不让多个执行器争用鼠标和键盘。

**五、窗口选择与捕获**

窗口选择界面展示可选应用窗口及必要的识别信息。确认选择后，绑定窗口句柄、进程身份和当前几何信息。

只将所选游戏窗口的图像交给模型。程序自己的主窗口和悬浮窗不作为游戏观察输入。

需要处理：

- 窗口移动和缩放。
- Windows DPI 缩放。
- 多显示器和负坐标。
- 窗口最小化、关闭或重建。
- 同名窗口。
- 黑屏、无有效帧和捕获失败。

目标窗口失效时停止输入，并提示重新选择。

新一次启动不能直接复用旧窗口句柄。可以提供候选匹配，但必须核验新的目标身份。

预览更新和模型调用使用不同节奏：本地持续观察，模型按剧情变化调用，不逐帧请求模型。

**六、剧情识别和 Agent 循环**

核心循环：

获取画面 → 判断剧情状态 → 组装上下文 → 请求模型 → 校验动作 → 执行一次 → 重新观察 → 保存记录。

识别状态至少包括：

- 对话文字显示中。
- 完整对话。
- 选项。
- 转场或加载。
- 菜单。
- 未知界面。

注意第一次点击可能只让文字显示完整，第二次才推进。禁止连续盲点跳过未读取剧情。

不能仅用整张画面的像素变化判断剧情更新。人物动画和背景变化需要与对话、选项变化区分。

通用模式通过视觉模型识别；可选游戏配置用于记录对话区域、推进按键、等待时间等，提高稳定性。配置不作为新建会话的必填项。

模型每次只提出一个动作。允许的动作包括：

- 等待。
- 推进一次对话。
- 选择某个选项。
- 点击游戏客户区内的位置。
- 按一次允许的按键。
- 请求人的帮助。

动作使用明确的结构化格式，绑定观察 ID、运行版本和必要的窗口信息。

模型不拥有任意脚本、系统命令、文件操作或其他窗口控制工具。游戏画面内容作为观察数据处理，不能改变执行器的权限。

模型请求失败可以有限重试；已执行的鼠标和键盘操作不能因请求重试而再次执行。

**七、输入执行与暂停**

将输入执行独立封装，模型不能绕过执行器直接操作系统。

执行前检查：

- 会话仍然存在且处于允许执行的状态。
- 运行版本仍然有效。
- 目标窗口和进程仍然有效。
- 游戏窗口在前台且未最小化。
- 点击位置在游戏客户区内。
- 点击位置没有被其他窗口或悬浮窗遮挡。
- 窗口尺寸、位置及坐标映射仍然有效。
- 对话或选项状态没有使动作过期。
- 用户没有暂停、接管或发出新的引导。

禁止模型使用 Windows 键、切换应用等系统快捷键。具体游戏所需的普通按键通过白名单配置。

窗口失焦时等待或暂停，不持续抢回焦点。

需要明确：系统模拟输入加前台检查属于应用层约束，仍然存在焦点变化的竞态，不能称为系统级的单窗口沙箱。如果需要严格隔离，应支持后续将游戏和执行器放入独立隔离环境。

暂停指令优先于模型请求。暂停时：

- 立即禁止后续动作。
- 清空待执行动作。
- 递增运行版本。
- 尽可能取消未完成请求。
- 拒绝之后返回的旧响应。
- 释放由程序持有的按键和鼠标状态。

已经发出的输入无法撤回。界面准确表达暂停已阻止后续动作，而非声称撤销已发生的操作。

如果前端连接丢失、桌面外壳异常退出或控制通道超时，后台执行器停止继续输入。

**八、悬浮窗与人的引导**

提供独立置顶悬浮窗，复用前端组件。

展示：

- 当前会话名称。
- 当前运行状态。
- 对剧情的简短理解。
- 下一步动作和简短理由。
- 暂停、接管和继续。
- 引导输入框。

观看状态尽量不抢游戏焦点。用户进入输入或接管状态时先暂停操作。

引导至少支持：

- 仅下一步生效。
- 持续生效，直到用户取消。

引导保存在所属会话中，并记录生效范围。

模型请求过程中收到引导时，旧请求结果不得执行。恢复时重新观察画面，并使用新的引导重新决策。

模型调用不能阻塞界面和暂停按钮。

模型给出的简短理由作为其输出记录，不将其描述为内部思考过程的完整还原。

**九、长剧情记忆**

完整历史保存在本地，但不能在每次请求中发送全部历史。

采用分层上下文：

- 当前截图。
- 最近对话和动作。
- 当前场景摘要。
- 此前章节摘要。
- 关键事件。
- 人物关系。
- 尚未确认的判断和问题。
- 当前有效引导。

区分剧情事实、模型推测和不确定信息。

重要记忆关联原始记录，允许回查。摘要记录来源范围、版本以及处理到的事件位置。

按模型上下文容量设置预算。摘要或请求失败不能删除原始历史。

所有摘要、检索和上下文构建必须限定到当前会话。恢复旧检查点时，不能带入检查点之后的剧情。

**十、持久化和关闭后续玩**

从第一版实现持久化，不能最后再补。

需要保存：

- 会话名称和 ID。
- 模型配置引用及运行参数快照。
- 对话与观察事件。
- 模型请求和响应，进行必要脱敏。
- 决策、动作及执行结果。
- 剧情摘要和人物记忆。
- 人的引导。
- 检查点。
- 最近画面。
- 可选游戏存档备注。

采用持续记录和事务，不只依赖退出时保存。

动作生命周期至少区分：

已提出 → 已校验 → 准备执行 → 已发送 → 已观察结果。

如果程序在动作发送后、结果记录前崩溃，恢复时标记为结果未确认，重新观察，禁止自动重放。

正常退出顺序：

停止接收新动作 → 使未完成请求失效 → 保存检查点 → 停止捕获和执行 → 关闭后台。

重新启动后加载会话列表。恢复会话默认暂停，不自动开始点击。

区分两种恢复情况：

1. 游戏还开着：重新绑定窗口，读取当前画面并核对进度。
2. 游戏已关闭：用户启动游戏、载入存档，再绑定窗口和恢复会话。

Agent 检查点不能代替游戏存档。第一版支持游戏内手动存档，并可记录存档位置和截图；自动快速存档按游戏配置后续适配。

如果载入的是较早游戏存档，提供选择对应 Agent 检查点的方式。画面无法确认时允许用户校正恢复位置，不假定截图相似就代表全部游戏状态一致。

**十一、记录与模型比较**

为后续比较不同模型保留完整记录能力。

记录：

- 会话和运行段 ID。
- 模型标识及实际配置。
- 提示词版本。
- 输入截图和上下文范围。
- 识别出的选项。
- 选择和简短理由。
- 实际执行结果。
- 人类干预。
- 请求耗时。
- 服务实际返回的用量信息。

不同服务不支持的参数明确记录，不假定相同温度或随机种子能保证跨模型等价。

支持查看历史时间线和导出脱敏记录。

新会话只要求名称。复杂实验模板和检查点分叉可以后续扩展，不增加首版创建流程的必填项。

**十三、实施阶段**

按以下顺序完成，各阶段保留可运行结果：

1. 建立前后端、桌面外壳、数据库和独立会话结构。
2. 完成模型配置、会话新建/重命名/删除、窗口选择和预览。
3. 完成受控的单步鼠标键盘执行、暂停及失焦处理。
4. 接入视觉模型，完成读取对话、推进和选项决策闭环。
5. 完成悬浮窗引导、旧响应作废及异常恢复。

7. 完成历史回放、导出、真实游戏验证和 Windows 打包。

会话隔离和持久化从第一阶段建立，后续阶段完善行为。

**十四、验证和交付标准**

测试重点包括：

- 不同会话记忆不混用。
- 重命名保留数据。
- 删除后旧响应不能执行或重新生成数据。
- 暂停和引导能阻止迟到响应。
- 窗口移动、缩放、DPI 变化后坐标准确。
- 失焦、关闭和遮挡时拒绝不合适的输入。
- 网络重试不导致重复动作。
- 正常关闭后恢复。
- 异常退出后识别未确认动作。
- 恢复较早检查点时不携带后续剧情。
- 密钥不出现在日志和导出中。
- 打包应用能启动后台并正常退出。

可建立模拟对话窗口和模型响应进行自动验证，再用实际 GAL 验证完整流程。模拟测试和真实模型、真实游戏测试分别报告。

最终验收流程：

打开应用 → 创建并命名会话 → 配置模型 → 选择游戏窗口 → 开始 → 读取剧情并选择 → 悬浮窗引导 → 暂停关闭 → 重新打开 → 恢复会话及游戏进度 → 继续 → 切换另一独立会话。

交付可运行代码、启动说明、打包方式、配置说明、已验证能力和兼容性限制。

如果缺少真实模型凭据或游戏环境，继续完成可独立验证的部分，并准确说明哪些端到端能力尚未验证。

常规实现选择自行推进。需要用户输入时只询问真正影响实现的缺失信息，不反复确认已经确定的需求。不要将尚未实现的按钮、模拟响应或未经验证的恢复能力描述为已完成。
